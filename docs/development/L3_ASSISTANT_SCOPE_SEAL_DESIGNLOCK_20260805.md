## 1. Framing: seal now, redesign later — two different asks, not one

Finding #5–#7 above describe a **dangerous path**, in #530's own vocabulary: a live, deployed, mounted service that can route arbitrary user input to hosted third-party LLM providers, with no documented redaction boundary, sitting directly adjacent to customer-drawing data (via its own tool layer, finding #10) and a degraded retrieval substrate (finding #7) it does not honestly disclose per-response.

Two asks follow, and they are **not the same size or the same gate**:

- **§2 (SEAL) — a no-regrets action, in scope for safe-park now.** Fail-closed defaults, an explicit egress boundary. Needs no new customer data, no new model environment, no product decision about the assistant's fate. Correct under *all three* of #530's end states — sealing a dangerous default doesn't cost anything if the module is later mothballed, folded in, or kept.
- **§3 (REDESIGN) — a product decision, explicitly NOT authorized by this lock.** Narrowing the module's *purpose* to "explain this platform's own decision evidence" is only worth doing if the "continues as an independent product" end-state wins. It needs a named owner and a customer-facing rationale `PRODUCT_STRATEGY.md` §7.2's definition-of-done requires ("its product owner and user are named"). This lock describes the target shape so a *future*, separately-ratified implementation has something to build against — it does not authorize starting that work now.

## 2. SEAL — the immediate, no-regrets target contract

Mirrors the pattern already used for `/model/reload` (#513/#516) and production-identity defaults (#517): **fail-closed first, redesign later, never a flag that silently re-opens the sealed path.**

### A. Provider default: local-only unless explicitly opted in — every LLM-egress path, not just one, and verified by endpoint not by name
- **Scope: this requirement governs all three egress-capable paths under `src/core/assistant/` (finding #13), by name** — `CADAssistant`'s provider resolution + `_fallback_generate`; `FunctionCallingEngine.__init__` (whose default constructor argument is currently `llm_provider="claude"` — the most severe of the three, since no error or fallback is required to trigger it, only a present API key); and `MultiModelAssistant._create_provider` / `ModelSelector.select_with_fallback`. A seal that only covers `CADAssistant` leaves the other two open.
- With no explicit, per-deployment configuration, provider resolution **MUST** land on `OfflineProvider` (or a verified-local `OllamaProvider`/`VLLMProvider`, see below) on **every** path — never a hosted provider by default. Consistent with §2.1's on-premise/private-network requirement. `FunctionCallingEngine`'s default argument specifically **MUST** change from `"claude"` to `"offline"` (or equivalent) — a default that requires an explicit override to reach a hosted provider is the seal, not a default that requires an explicit override to avoid one.
- Selecting `ClaudeProvider` / `OpenAIProvider` / `QwenProvider` / any non-local `VLLMProvider` **MUST** require an explicit opt-in flag documented as an external-provider-egress event under the same governance as any other external AI call (§4's "customer drawings stay private by default; external-provider transmission is explicit opt-in" rule, and §8.3's pilot release gates) — not merely "configure an API key and it works."
- **The seal covers the fallback/failover path, not only the initial default (finding #11).** When the explicitly-opted-in (or default local) provider errors, the fallback chain — `CADAssistant._fallback_generate`'s `["claude","openai","qwen","vllm","ollama"]` order, **and** `ModelSelector.select_with_fallback`'s priority/health-based selection in `MultiModelAssistant` — **MUST NOT** attempt any hosted provider that was not itself part of the explicit opt-in. The opt-in decision governs every attempt for a request across all three paths, not just the first one on one of them.
- **"Local" is verified by endpoint, not asserted by provider class name (finding #14).** `OllamaProvider`/`VLLMProvider` resolving `OLLAMA_BASE_URL`/`VLLM_ENDPOINT` to anything other than a loopback address or an explicitly per-deployment-allowlisted private host **MUST** be treated as external egress requiring the same opt-in as a hosted provider — selecting "Ollama" is not by itself proof of a local, non-egress request.
- A provider class whose required SDK (`anthropic`, `openai`) is not installed **MUST** fail closed to `OfflineProvider` at selection time, not raise an unhandled `ImportError` or silently degrade mid-request (verify current behavior — not yet checked; this lock flags it as a thing to verify, not asserts it either way).

### B. Egress boundary: a field-level allowlist schema, not a category description
- A payload sent to a hosted provider **MUST** be validated against an explicit, field-level allowlist schema — not merely "computed §3.3 fields are OK." §3.3's own field list (candidate id, provenance, evidence/rejection reasons, drawing numbers implied by provenance, supplier/material/process notes) can itself carry customer-sensitive identifiers even though every value is "computed," not raw. The schema **MUST**, by default: redact or hash candidate/file identifiers (no plaintext IDs that trace back to a customer's part/drawing numbering scheme); exclude supplier names, drawing numbers, and free-text process/material notes unless a field is explicitly allowlisted per-deployment; permit only the minimum needed for the explainability purpose (scores, confidence, rejection-reason *category*, not verbatim customer-authored text).
- Raw drawing bytes, raw OCR text, and file paths remain categorically excluded (unchanged from the original draft) — the schema requirement above is additive, not a replacement.
- A tool call (`similarity_tool`, `classify_tool`, etc.) whose result is destined for a hosted-provider payload **MUST** pass through the same schema-validated redaction boundary before the network call, not after.

### C. Honest degradation disclosure: structured status, not a log line or a free-text note (extends #503; closes finding #12)
- Any computation that did not complete as designed — the embedding/retrieval TF-IDF fallback (already governed by `PHASE0_A3_HONEST_EMBEDDING_DEGRADATION_DESIGN_20260708.md` / #503), **and every one of the 9 `TOOL_REGISTRY` tools' exception paths** (finding #12: all 9, not a subset — `classify_tool`, `similarity_tool`, `cost_tool`, `feature_tool`, `process_tool`, `quality_tool`, `knowledge_tool`, `graph_knowledge_tool`, `pointcloud_tool`) — **MUST** carry a **canonical, schema-checkable** `status` field whose value is exactly one of `failed` / `unavailable` / `degraded`, not only a log line or a free-text `note`, and not a tool-specific string standing in for the enum. Free-form detail (e.g. *which* model was unavailable, *why* a call degraded) belongs in a separate `reason_code` field, not in `status` itself.
- `pointcloud_tool.py`'s existing top-level `status` field (currently valued `"model_unavailable"`) is the **structural** pattern to generalize to the other 8 — the requirement asks for consistency with an invariant already present in the codebase, not a new one. Its *value* still needs normalizing to fit the canonical enum: e.g. `status="unavailable", reason_code="model_unavailable"`.
- A degraded/failed tool result **MUST NOT** be citable as decision evidence: no fabricated business-looking values (e.g. `cost_tool`'s hardcoded CNY cost breakdown, `process_tool`'s hardcoded process/material map, or any other tool's plausible-looking default) may be returned in place of a clearly-marked absence. Where a placeholder value is structurally required, it **MUST** be paired with the `status` field above, not stand alone.
- **A free-text `note` field is not sufficient disclosure, and the system prompt must not instruct hiding it either way (finding #15).** `function_calling.py`'s current system prompt explicitly instructs the LLM to *not* surface a tool's `note`-field content to the user ("如果工具返回结果中含有 note 字段，不需要向用户暴露内部错误细节"). Once tools carry a structured `status` field, the system prompt and every response-assembly path **MUST** treat a non-`ok` status as something to disclose or refuse to answer from — never something to suppress.
- This is one invariant, not two or three: the same "never let a degraded/failed computation look like a real result" principle governs the retrieval substrate, all 9 tools, and the assembled response the user actually sees. An implementation must not treat these as separate problems with separate fixes.

## 3. REDESIGN target (described, not authorized) — for a later, separately-gated lock

If a future decision (owner-named, customer-facing, per §7.2) keeps this module as part of the product:

- **Scope narrows from general-purpose to own-evidence explainability.** Every response about a specific candidate/decision traces to a §3.3 decision-contract field; general-purpose content generation unrelated to a specific evidence bundle (reports, slides, free-form chat) is out of scope — that capability already exists in the market (Tencent WorkBuddy and peers) and competing on it contradicts this platform's narrow-wedge bet, not just §6's letter.
- **Placement**: assistant output surfaces inside the existing evidence-review flow (§3.1's boundary: recall → verification → evidence bundle → human decision), not as a separate destination requiring a context switch — unverified whether this is already true; a question for implementation, not this lock.
- **No new remote-dispatch/IM-bot/notification-channel integration** (WeCom/DingTalk/Slack-style) is authorized by any future work here without a named customer request — §6's "no adapters without a named consumer" applies at full force.
- **RAG substrate fix** (replacing the TF-IDF fallback with real embeddings) is its own evidence-integrity work, gated the same way as Track E, not bundled into this module's redesign.

## 6. Verification contract (what SEAL implementation must make impossible)

At contract altitude, for the eventual SEAL implementation PR:

1. No explicit opt-in configured → a request through **any of the three egress-capable paths** (`CADAssistant`, `FunctionCallingEngine` — including its bare default construction with no arguments — `MultiModelAssistant`) that would otherwise route to `ClaudeProvider`/`OpenAIProvider`/`QwenProvider` → **fails closed** to `OfflineProvider`, not silently succeeds against a hosted endpoint. Constructing `FunctionCallingEngine()` with zero arguments must not, by itself, be capable of a hosted-provider call.
2. **(closes finding #11, extended to finding #13's second path)** Force the opted-in-or-default primary provider to error on **both** `CADAssistant._fallback_generate` and `MultiModelAssistant`/`ModelSelector.select_with_fallback` → assert the resulting fallback/failover attempt sequence contains **zero** hosted-provider calls when no hosted provider was part of the explicit opt-in — not merely that the *final* response came from a local provider (an implementation could satisfy that while still having attempted, and partially transmitted a prompt to, a hosted provider along the way; the discriminator must catch the attempt, not just the outcome).
3. **(closes finding #14)** Point `OLLAMA_BASE_URL`/`VLLM_ENDPOINT` at a non-loopback, non-allowlisted host → the resulting provider selection is treated as external egress requiring opt-in, **not** silently accepted as "local" because the provider class is `OllamaProvider`/`VLLMProvider`.
4. A hosted-provider call payload is validated against the field-level allowlist schema (§2.B) → **rejected before the network call** if it contains raw image bytes / raw OCR text / file-path strings, an un-redacted candidate/file identifier, or any field not on the explicit per-deployment allowlist.
5. **(closes finding #12, extended to all 9 tools)** Inject a forced exception into **every** `TOOL_REGISTRY` entry in turn (iterate the registry — `classify_tool`, `similarity_tool`, `cost_tool`, `feature_tool`, `process_tool`, `quality_tool`, `knowledge_tool`, `graph_knowledge_tool`, `pointcloud_tool` — not a named subset, so a future tool added to the registry inherits the discriminator automatically) → assert the returned payload carries `status` **exactly equal to** one of `{failed, unavailable, degraded}` (not a tool-specific string such as `pointcloud_tool`'s current `"model_unavailable"`, which belongs in a `reason_code` field instead), as a structured field, not only a log line or a free-text `note`; and that response-assembly code refuses to present that result as decision evidence (e.g. it cannot populate a `_decision_evidence_from_metadata`-style citation from a `status`-marked result).
6. **(closes finding #15)** With a tool result carrying a non-`ok` `status`, assert the system prompt / response-assembly path does **not** instruct or cause suppression of that status from the user-visible answer — the opposite of `function_calling.py`'s current instruction.
7. A response whose retrieval used the TF-IDF fallback and does **not** carry the disclosed-fallback marker → **flagged as a regression** against the #503 invariant (same structured-status requirement as #5, applied to the retrieval substrate).
8. `anthropic`/`openai` uninstalled (the current, verified state) → provider selection resolves to `OfflineProvider` deterministically, not an unhandled exception surfaced to the caller, on all three egress-capable paths.
